# Подготовка GitHub Release 1.3.0

Публикация не выполняется этим документом. Установщик настроен на tag
`v1.3.0`, пакетную версию `1.3.0-r1` и базовый URL:

`https://github.com/quargelk/easy-vless/releases/download/v1.3.0`

## Подготовить assets

Сборки уже лежат в `dist/sing-box-lx-integration/`; повторная сборка не нужна.
Проверить их суммы и собрать плоскую папку assets:

```sh
for f in dist/sing-box-lx-integration/*/SHA256SUMS; do
  (cd "${f%/*}" && sha256sum -c SHA256SUMS) || exit 1
done
sh scripts/prepare-release-assets.sh
cd dist/release-assets-1.3.0-r1
sha256sum -c SHA256SUMS
```

Скрипт сверяет локальные четыре манифеста, проверяет совпадение одноимённых
пакетов, объединяет одинаковые architecture-independent assets, добавляет
четыре ABI-пакета sing-box-lx и `install.sh`, затем формирует один общий
`SHA256SUMS`. Результат — 15 загружаемых файлов плюс сам манифест. Все имена
совместимы с `pkg_file()` в installer. Этот манифест обеспечивает целостность,
но для IPK не является криптографической подписью релиза.

GitHub Release assets загрузить плоским списком файлов из этой директории.
Не загружать четыре исходных `SHA256SUMS`: их заменяет общий манифест.
Черновик выпуска можно подготовить отдельно, но `gh release create`, push tag
и публикацию выполнять только после отдельного разрешения.

## Блокер доверия APK

APK из имеющихся комплектов не подписаны. SDK 25.12.6 `package-pack.mk`
вызывает `apk mkpkg` без `--sign-key`; в `scripts/sdk-build.sh` подпись
появляется только при явно заданном `EV_APK_SIGNING_KEY`, которого при
первоначальной сборке не было. `apk verify` 3.0.5 возвращает
`UNTRUSTED signature` и для этих файлов, и для контрольного unsigned APK.
Это поведение не свидетельствует о неподдерживаемом формате или неизвестном
подписанте: у исходных пакетов нет производственной подписи.

Для выпуска без пересборки подготовлен `scripts/sign-release-apks.sh`.
Он копирует комплект, подписывает каждый APK командой `apk adbsign`, выводит
только публичный PEM, проверяет все APK с чистым временным trust root и
перегенерирует `SHA256SUMS`. Он не устанавливает ключ в систему и не принимает
решение за пользователя о доверии. Воспроизводимая команда с ключом из
защищённого хранилища:

```sh
APK_TOOL=/path/to/openwrt-25.12.6-sdk/staging_dir/host/bin/apk \
  sh scripts/sign-release-apks.sh \
  dist/release-assets-1.3.0-r1 \
  dist/release-assets-1.3.0-r1-signed \
  /secure/path/easy-vless-release.rsa
```

Приватный ключ не помещать в репозиторий, assets, логи или обычный CI cache.
Публичный `easy-vless-release.pem` должен быть передан клиентам по независимо
доверенному каналу и установлен в `/etc/apk/keys/` до `apk verify`/`apk add`.
OpenWrt 25.12.6 сам устанавливает публичный ключевой набор в этот каталог
([Makefile openwrt-keyring 25.12.6](https://git.openwrt.org/openwrt/openwrt/tree/package/system/openwrt-keyring/Makefile?h=v25.12.6)).
Не скачивать и не устанавливать ключ автоматически из того же Release URL до
проверки пакета: это не создаёт независимую цепочку доверия.

До публикации или установки APK-выпуска необходимо выбрать production-ключ и
доверенную схему распространения публичной части:

1. Уполномоченный владелец выпуска генерирует production-ключ в защищённом
   окружении или secret manager, выбирает ротацию/резервирование и передаёт
   только публичный ключ и fingerprint отдельным доверенным каналом.
2. Запустить signing helper для release assets, пересчитать общий
   `SHA256SUMS` после подписи и сохранить приватный ключ вне рабочего дерева.
3. Предварительно установить публичный ключ по независимому каналу и
   подтвердить `apk verify`, `--check` и тестовую установку в чистом OpenWrt
   25.12.6 rootfs.

Тест helper выполнен на apk-tools 3.0.5 с одноразовой RSA-парой: он подписал
все 7 APK assets, `apk verify` принял их в изолированном root только после
добавления соответствующего тестового PEM. Без ключа проверка отказала.
Временная пара удалена и не входит в проект. Production-подписи пока нет.
Не публиковать приватный ключ и не включать `--allow-untrusted` для удалённого
GitHub Release. До выполнения перечисленных шагов APK-выпуск не готов к
безопасной установке на чистый роутер.

игнорируемые `dist/`, release assets, сохранённые архивы, целевые временные
логи и 16 362 уникальных Git blob по всем доступным локальным refs. Целевые
проверки не нашли приватных ключей, известных форматов API-токенов или
не-placeholder VLESS/Trojan ссылок в Git-истории и проектном release bundle.
Совпадения тестовых URL ограничены `example.*`, зарезервированными адресами
и синтетическими тестовыми значениями.

`dist/tr3000-lx-trial/recovery/router-baseline.tgz` с резервными конфигурациями

данные/ключи; значения не выводились и архив не менялся. Он игнорируется Git,
не включён в source/release backup, signing output или assets. Хранить этот
файл как конфиденциальный; не публиковать и не добавлять в архивы выпуска.
В исходниках и истории высокоуверенных секретов не найдено, поэтому ключи
перевыпускать на основании этого аудита не требуется.

## Проверка установщика

Скачать скрипт с release URL. `--check` выполняет проверки устройства, HTTPS,
фидов, зависимостей, размера и release assets, скачивая их только во временный
каталог; установки и изменения системы не выполняет:

```sh
wget -O /tmp/easy-vless-install.sh \
  https://github.com/quargelk/easy-vless/releases/download/v1.3.0/install.sh
sh /tmp/easy-vless-install.sh --check
```

Для доверенного HTTPS mirror, где доступны те же имена assets и общий
`SHA256SUMS`, применить:

```sh
sh /tmp/easy-vless-install.sh --check --base-url https://mirror.example/releases/v1.3.0
```

`--base-url` принимает только HTTPS и отключает автоматические сторонние
зеркала. После публикации провести проверку release URL и зеркала в OpenWrt
rootfs 24.10/IPK и 25.12/APK; обычный Linux-хост не является заменой `--check`
на OpenWrt. Не запускать установку на физическом TR3000 в рамках подготовки
релиза.
